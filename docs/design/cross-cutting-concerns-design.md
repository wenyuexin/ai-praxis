# 横切维度设计（Cross-Cutting Concerns）

> **状态**：设计透镜 / rationale（初稿）。本稿解释"横切维度该不该物理抽取、该怎么和领域主轴共存"，**不是运行态落位规则**——具体某篇文档该放哪里，仍按 [`organization-principles.md`](../contributing/rules/organization-principles.md) 和 [`place.md`](../capabilities/place.md) 判断。
> **触发**：2026-10-12 关于"理想目录划分"提案的多轮讨论（提案为本地临时研究记录，未入库），核心争议是 frameworks-and-tools / evaluation / memory 应否从领域目录中抽出单独集中存放。
> **证据**：问题诊断部分基于本仓库实际文件系统核查（Observed）；通用原理部分是本次讨论归纳（Inferred）；具体案例判断引用了已核查的文件路径与内容。

## 1. 这份文档解决什么

仓库里存在一类反复出现的结构疑问：某些内容同时具有"领域归属"和"类型归属"两个维度，比如：

- 一篇 LangGraph 研究，既属于"agentic 领域"，又属于"框架类对象研究"；
- 一篇 RAG 评估方法笔记，既属于"rag 领域"，又属于"评估类研究"；
- 一篇 memory 检索策略笔记，既属于"agentic 领域"，又可能与"rag 的检索方法"是同一类技术。

当有人提出"把所有框架研究/评估研究/记忆研究集中到一个新顶层目录"时，这个问题会反复被重新讨论一次。本文把这类问题收敛成一个统一判断框架，避免每次都从零推演。

## 2. 为什么会反复出现这个问题：单轴树形结构的维度取舍

目录树只能表达一个主维度的层级关系。当一份内容同时具有"领域"和"类型"两个同等重要的维度时，无论选哪个做主轴，另一个维度都会被降级，只能靠文件名、交叉引用或索引页去补偿。

这不是分类轴选错了，是树形结构面对多维信息时的结构性限制：

```text
领域做主轴 → 类型维度降级：
  好处：同领域内容物理相邻，创建和维护时的上下文（相邻概念、对比对象）天然连续
  代价：横切检索（"所有框架类研究"）没有天然入口，需要跨目录人工收集

类型做主轴 → 领域维度降级：
  好处：横切检索有天然入口
  代价：同类型、不同领域的内容被物理拉近，但它们在创建和维护时的上下文并不相关
       （LangGraph 研究引用的是 agentic 内部概念，MegaTrain 引用的是 training-infra 内部概念，
        物理相邻不创造协同，只增加落位判断成本）
```

两种选择的代价是对称的，不存在无代价的"更合理"选项。真正可以优化的，不是"选哪个做主轴"，而是**被降级的维度能不能用比"物理合并"更轻的方式补偿**。

## 3. 判断标准：创建/维护上下文决定主轴，检索需求靠索引补偿

一份内容该不该被归入横切目录，优先问：

1. **它的创建和维护上下文主要来自哪个维度？** 一篇研究写作时，自然引用、对比、关联的"邻居内容"属于领域还是属于类型？邻居在哪个维度上更密集，主轴就该选哪个维度。
2. **横切检索需求是真实存在、还是理论上可以存在？** 如果从未有人真正需要"跨领域看所有框架研究"，这个需求不构成改变主轴的理由。
3. **如果横切检索需求是真实的，是否可以用索引/聚合页满足，而不必物理合并？** 索引页只改变查找路径，不改变创建和维护时的物理位置，成本远低于物理重构。

`auxiliary-layers-design.md` 已经在元信息文件（`temp/`、`notes/`、`backlog/candidates/conflict/roadmap`）这个问题上验证过同样的判断——那些文件天然散布在每个领域目录下，该文档的解法是"加一层横切视角去解释它们如何配合"（§2、§5.6），而不是把它们物理合并成一个新目录（§5.6："聚拢靠概念，不靠物理嵌套"）。本文把同一判断框架套用到知识正文层面的横切维度上。

## 4. 三个具体案例的交叉判断

### 4.1 frameworks-and-tools：维持领域主轴，不抽取

**现状事实**（已核查）：全仓库不止 `agentic/06-frameworks-and-tools/`（131 篇）一处有框架/工具类对象研究，`training-infra/03-frameworks-and-tools/MegaTrain.md` 也是同一种研究模式——对一个具体项目做系统化拆解。两者内容形态一致，区别只是前者已经长成成熟体系，后者刚起步。

**创建/维护上下文判断**：一个可观察到的案例是，一篇 LangGraph 研究的邻居是 agentic 内部的 planning/memory/tool-use 概念；一篇 MegaTrain 研究的邻居是 training-infra 内部的分布式训练概念。这个样本说明两者的维护上下文可能不同，不能仅凭"都属于框架/工具"就推断物理合并会创造协同；但样本数量仍然有限，不足以把该判断写成所有领域的已验证事实。

**[`agentic/06-frameworks-and-tools/README.md`](../../agentic/06-frameworks-and-tools/README.md) 已有的边界声明**（第 7 行）："`06-frameworks-and-tools/` 不负责重新讲解 Agent 的底层能力体系，而负责分析现实框架、工具和项目如何实现、组合、产品化这些能力。" 这证明 agentic 内部已明确区分能力知识与对象研究；但单个领域的 README 和 `training-infra/03-frameworks-and-tools/MegaTrain.md` 还不足以证明全仓已有统一、稳定的 frameworks-and-tools 模式。

**暂定结论**：目前没有足够证据支持将所有领域的框架对象研究物理合并到 `systems-and-engineering/`；跨领域样本有限，且现有目录命名和层级并不一致。优先保留各领域的对象上下文，同时评估是否需要一个横向索引。若后续发现跨领域对象确有共同的维护流程、稳定共享的比较维度，且不需要在统一目录里按领域重建分类，则应重新评估物理抽取，而不能把"领域内邻居不同"当作永远不抽取的规则。

### 4.2 evaluation：维持领域主轴，不抽取

**现状事实**（已核查）：`agentic/07-evaluation/` 评估的是 agent 系统本身（任务完成度、SWE-bench 这类 agent 专属 benchmark，见 `agent-benchmarks/`、`task-completion-metrics/`）；`rag/04-evaluation/` 评估的是检索/生成质量（RAGAS、TruLens 这类 RAG 专属指标）。但 `embodied-intelligence/07-evaluation-and-benchmarks/` 当前 README 标题和主体实际整理的是 VLA/具身模型训练数据与综述论文，不是评估内容；其上层 README、index 和根 README 已标注该目录当前承载训练数据与综述资源、等待拆分。这是已确认的局部目录语义错位，不应继续作为“评估内容”的样本使用。

**创建/维护上下文判断**：评估方法的设计高度依赖被评估对象的特性。已有目录名称和 README 定位至少显示，agent 评估关注 Agent 系统任务完成、可观测性与可靠性，RAG 评估关注检索/生成质量；两者存在可共享的评估方法，但被评估对象、失败模式和指标解释上下文并不完全相同。因此目前不能仅凭"都属于 evaluation"推断物理合并会创造协同。

**暂定结论**：现有有效样本说明评估内容与被评估领域紧密相关，但具身目录目前存在明显错位，不能拿它作为评估分类已经运行良好的证据。跨领域共享的方法、工具和维护流程仍未被系统比较。因此，当前不宜直接把它们物理合并到 `evaluation-and-reliability/`；也不能断言任何统一评估层必然没有净收益。需要进一步比较：共用的评估方法是否足以成为统一组织和维护的主体，还是领域特定指标、任务和失败模式仍是主要内容。若横向检索是当前唯一收益，索引页成本更低；若共享方法已形成独立、持续维护的知识体系，统一层才值得试点。

### 4.3 memory：不是组织结构问题，是未解决的内容边界问题

**现状事实**（已核查）：[`agentic/02-single-agent/memory/README.md`](../../agentic/02-single-agent/memory/README.md) 全文完全没有提到 RAG 或 knowledge graph；其"不放在这里"清单（第 19 行）只列了多智能体共享状态、tool-use、environments 三项，**没有对照 `rag/02-retrieval/`**。`memory/retrieval-methods/` 目录讨论"检索触发、召回策略、排序过滤"，与 `rag/02-retrieval/`（vector-databases、advanced-retrieval 等）的技术范畴高度相似，但两边 README 互相不引用、不声明边界。反向检查，`rag/README.md`、`knowledge-graph/README.md` 同样未提及 memory。

**这与前两个案例的本质区别**：frameworks-and-tools 和 evaluation 的横切争议纯粹是"组织结构选择"——内容边界清楚，只是讨论要不要换个物理位置。memory 这里，物理位置之外还存在一个未被回答的问题：memory 的检索方法和 RAG 的检索方法，内容上到底是不是在重复建设同一组技术。这个问题不会因为"抽到一起"或"继续分开"而自动解决，先搬目录不能替代先把边界讲清楚。

**结论**：

1. 先做内容核查：对照读 `memory/retrieval-methods/` 和 `rag/02-retrieval/` 的实际内容，判断是否存在实质重复。
2. 如果存在重复，不是靠换父目录解决，而是在内容层面收敛——通用检索技术的正文归 `rag/02-retrieval/`，`memory/retrieval-methods/` 只保留"该技术应用于 agent 记忆场景时的特殊约束"这类差异化内容，用引用代替复制。
3. 如果核查后确认两者讨论的技术确实不同（比如 memory 侧重的是"记忆写回、压缩、过时判断"，RAG 侧重的是"外部知识库的检索召回"），则在两边 README 的"边界说明"里各补一条明确的交叉引用声明，把这个判断沉淀下来，避免下次又重新讨论一遍。
4. 这项内容核查目前尚未执行，是本文档遗留的待办，不是本文档本身要给出的结论。

### 4.4 对象研究的唯一规范归属：不能由横切目录问题顺带解决

本次讨论还暴露出一个与"是否抽取 frameworks-and-tools"不同、但必须单独处理的问题：具体对象研究同时可能被理解为领域内机制研究，也可能被理解为框架/工具/项目对象研究。

以 Mem0 为例，当前对象研究位于 `agentic/02-single-agent/memory/project-studies/mem0/`，而 `agentic/06-frameworks-and-tools/` 又明确承接具体框架、工具、产品和开源项目。Mem0 目录自身的 README 已经把对象本体、源码与版本、公开契约、能力边界和限制列为主要内容，并把记忆层共性分类与跨对象比较排除在外。由此可见，问题不是简单的"memory 是否应该移动到 knowledge-and-context"，而是：

- 对象研究的规范 owner 是对象所在的领域目录，还是统一的对象研究目录？
- 如果对象同时属于某个能力主题和工程对象集合，哪一侧保留对象正文，另一侧只保留机制结论与指针？
- `project-studies/` 的分类依据是领域内对象集合，还是全仓统一对象集合？

当前材料足以确认这是一个真实的结构设计问题，但还不足以直接确认 Mem0 必须迁入 `agentic/06-frameworks-and-tools/03-project-studies/`。在没有用 Mem0、Graphiti、Zep 等边界对象做对照试点前，不应把任一位置写成仓库级结论。

本文的暂定设计方向是：具体对象的版本、源码、契约和对象级限制应只有一个规范 owner；相关能力目录只保留稳定的共性结论、适用边界和指针，不复制完整对象研究。这个方向仍属于 `Inferred`，需要通过对象矩阵验证其是否比当前结构减少主文漂移和重复维护。

## 5. 不建议抽取的"抽象父节点分组"：单独说明

本次讨论还涉及另一类改动——给已有领域目录加一层抽象父节点（例如用 `02-models-and-representation/` 概括 `llm/cv/world-models`），这与前面三个横切案例不是同一类问题，不应混淆：

- 横切维度案例（frameworks-and-tools/evaluation/memory）争论的是"内容该物理放在哪个目录"，是落位问题；
- 抽象父节点分组不改变任何内容的物理位置，只是在现有领域目录之上加一层归类节点，是展示/理解问题。

抽象父节点分组本身的信息增量可能较低（运行态检索仍需同时知道父类名和子类名），其收益（人类心智模型层面的归类）也可能用说明文字或索引页实现，因此不应默认通过物理嵌套目录来表达。这类改动不移动正文，但仍会改变检索路径与导航接口；是否值得采用，要看它是否实际降低理解和导航成本，而不能仅凭"没有移动文件"就认为风险可忽略。

## 6. 本文给出的通用判断流程

遇到"是否应该把某类横切内容抽取到独立目录"的问题时，按以下顺序判断：

```text
1. 这类内容在不同领域下的创建/维护上下文（邻居概念）是否相似？
   相似 → 抽取可能创造协同，继续评估
   不相似 → 维持领域主轴，不抽取，跳到第 3 步

2. 抽取后，新目录内部是否仍需要按原领域再分一次？
   需要 → 抽取没有净收益，不抽取
   不需要 → 抽取可能有收益，可以推进

3. 横切检索需求是否真实存在（而非理论上可能存在）？
   不存在 → 不需要任何改动
   存在 → 用索引/聚合页满足，不物理移动正文

4. 是否存在内容层面的真实边界模糊（而非仅物理位置选择）？
   存在 → 先做内容核查和边界声明，这是正文层面的工作，物理搬动目录不能替代它
   不存在 → 这纯粹是组织结构选择，按前三步的结论执行即可
```

frameworks-and-tools、evaluation 在第 1 步就能排除抽取；memory 需要走到第 4 步，而且第 4 步的答案尚未确定。
