# Runtime / Development Design

本文回答：**这个仓库为什么要显式区分“运行态”和“开发态”两种模式、两者各是什么、边界在哪，以及为什么 `docs/` 层要为开发态单独设入口。** 它是 `docs/DEVELOPING.md`（开发态入口）与根 `AGENTS.md`（运行态入口）分工的实现依据。

它属于 design layer：不替代任何规则条文，只解释这套“双模式 + 入口分离”为什么成立、如何落到具体入口文件。

## 1. 问题：同一个 AI 两态同体，边界模糊会静默越界

这个仓库是“仓库即知识 agent”。**操作它的和改造它的，常常是同一个 AI。** 传统软件里，用户（运行态）和开发者（开发态）是不同的人、不同的界面，边界天然清晰；这里两态同体，如果不显式画界，一个本该“取用知识”的任务会不知不觉滑进“理解 / 修改治理”——而 AI 对自己的越界往往无感。

这不是假想：`../contributing/incidents/` 里已记录的两次失败（capability 前置路由被跳过、overview / landscape 被当场压平），都是这种滑移——运行态的导航任务撞上了本该开发态处理的治理理解。所以对本仓库，两态模糊不是“可以不管”的理由，恰恰是“必须显式分离”的理由。

## 2. 两条不同的轴：运行态 / 开发态 与 控制面 / 数据面

必须先说清：有两条容易被混为一谈、其实不同的轴。

- **运行态 / 开发态 —— 生命周期（模式）轴**：我在*使用*系统，还是在*改造*系统。
- **控制面 / 数据面 —— 功能角色轴**（借自网络工程）：控制面做决策与治理，数据面做执行与数据存储；关键是**两者都发生在运行时**——控制面是“运行时被强制执行的治理”，不是“开发期”。

两条轴只在“落到哪些文件”上交叉，不是同一回事：

- 开发态 AI 编辑的那批文件（规则 / 设计 / 决策流）= 运行态里充当**控制面**的那批文件。所以控制面文件“在开发态被作者化、在运行态被强制执行”，横跨两态。
- **数据面**在本仓库 = 知识正文本体（各 topic 目录），相当于传统应用里的 MySQL（记录内容 / “用户数据”）；它由运行态读写，不是开发态的产物。

因此“控制面 ≈ 开发态、数据面 ≈ 运行态”只是一个**跨轴的对应**，不是等价；当作等价会误判文件职责。

## 3. LLM 应用的特殊性：AI 在两态都在，但角色不同

传统应用：开发态主体是人（写代码），运行态是用户 + 部署好的程序；控制面由开发者设定，数据面由用户灌。

LLM 应用特殊在 **AI 在两态都在场**，但角色不同：

- **运行态的 AI**：在既定规则内*操作*——导航、取用知识、读写数据面，受控制面约束。它是“被治理的执行者”。
- **开发态的 AI**：*作者化并校验*控制面文件本身（改规则 / 设计 / 方法论）。它是“治理的作者 + 校验者”。

同一主体、两种角色——这是本仓库需要为两态分设入口的根本原因：入口的作用，就是让 AI 一进来就明确“这次我是执行者还是作者”。

## 4. 映射到 ai-praxis：2×2

把两条轴交叉，本仓库的工作落在四个格子：

- **运行态 × 数据面**：导航、取用知识、`ingest` 灌入新知识——“用系统 + 喂内容”。
- **运行态 × 控制面**：读并遵守规则（规则在运行时约束行为）。
- **开发态 × 控制面**：作者化 + 校验规则 / 设计 / 方法论——开发态的主体工作。
- **开发态 × 数据面**：少见，只在重构知识存储本身（大规模迁移）时发生。

控制面文件 = `../contributing/` + `docs/design/`（管流程与决策）；数据面 = 各 topic 目录的知识正文。

## 5. 术语：运行态即 `evolution-design.md` 的“日常态”

[`evolution-design.md`](./evolution-design.md) 用“日常态 / 开发态”，本文用“运行态 / 开发态”——**日常态与运行态是同一个意思**：在不修改控制面文件的前提下，收集、整理知识的过程。为统一口径：

- 以 **运行态 / 开发态** 为规范的模式轴术语；“日常态”是运行态的同义（早先）称呼。
- **evolution 本身就是运行态与开发态交替的过程**（交替是非线性、可级联的，不是规律的一来一回）。本文定义这两个模式*是什么*；`evolution-design.md` 描述它们*如何交替*（节奏与评价尺度见该文）。

两文因此是“模式（本文）”与“模式的交替过程（`evolution-design.md`）”的关系，不重复。

## 6. 为什么业界不强调两态，而本仓库要

主流 AI 工具切分指令的轴是“按路径 / 受众 / 常驻 vs 任务”，很少有“开发态 AI 入口”这一说。以下四类原因是**维护者作为人类开发者的分析判断，介于观察与推理之间**；部分论据（尤其“别人为何这么做”）可能永远没有确定答案，不应读作既成事实——这正是 [`evidence-assessment-rules.md`](../contributing/rules/evidence-assessment-rules.md) §4.2 所说的“不可约不确定”一类：

- **① 部分应用两态区分本就不清晰**——结构性原因（尤见于 LLM 应用，AI 两态同体）。
- **② 缺统一开发范式**——很多框架自建临时目录，开发者索性不维护持久的开发态文档。
- **③ 隐藏开发态文档**——多人协作下各人开发方式不同，直接提交难做文件分离。
- **④ 洁癖**——认为开发态文件只为开发、不该进仓库。

②③④是**偶然**的（范式不成熟、协作摩擦、取向），①是**结构性**的。而本仓库在四条上都不同：

- ①：两态同体的模糊已在本仓库造成真实事故（见 §1），所以更要画线。
- ②：本仓库把开发态文档（`docs/design/`、`meta-rules`）当一等公民养，而非丢给工具草稿区。
- ③：本仓库的开发态文档是**共享治理**，本就该提交；个人 scratch 才留本地。区分是“个人 scratch vs 共享治理”。
- ④：本仓库的**交付物本身就包含“治理方式”**，开发态治理层不是脚手架，是产品的一部分——事实上 `docs/design/`、`../contributing/` 已在版本库内。

结论：社区不做的理由，三条对本仓库不成立、一条反而要求本仓库做。显式分离两态是有据的选择。

## 7. 分离即“校验边界”

自我改进系统的一个观察（Observed，来自 2026 相关研究）：稳定的自我改进靠**强校验器（verifier）**而非强生成器——校验器与生成器分离、并被强化，系统才不发散。

本仓库里，[`../contributing/rules/meta-rules.md`](../contributing/rules/meta-rules.md)（§1 触发、§3 签核）+ evidence 分级 就是这个校验器。把**开发态（提议 + 校验治理改动）**从**运行态（取用知识）**里分出来，正是把校验器边界显式化。所以两态分离不与“知识 ↔ 方法论 co-evolution”（见 `evolution-design.md`）冲突，反而是让它不失控的纪律。

## 8. 落到入口（实现依据）

入口按**模式**分，不按面分：

- **根 `AGENTS.md` = 运行态入口**：取用知识 + 遵守规则，保持傻瓜式、精简；强制先读。
- **`docs/DEVELOPING.md` = 开发态入口**：改控制面（规则 / 结构 / 设计 / 方法论）时的第二跳入口，由根入口一条按任务类型的下潜触发器指过去（机制见 [`navigation-design.md`](./navigation-design.md) §4）。
- **`ingest`**（运行态 × 数据面）不单列入口，归运行态、走 [`../capabilities/ingest.md`](../capabilities/ingest.md)。

`docs/DEVELOPING.md` 的具体承接清单、根入口指针原文，已依本文落地。

## 9. 与其他 design 文档的边界

- 与 [`system-design.md`](./system-design.md)：后者给整仓的静态角色模型（运行时接口 / 行为约束层 / 知识承载层）；本文给“运行态 / 开发态”这条动态模式轴，是前者的补充，不重复。
- 与 [`navigation-design.md`](./navigation-design.md)：后者管入口 / 自导航的**机制**（保证入口、确定性跳转、下潜触发器）；本文说明**为什么要有开发态这个入口**，机制接线仍归 navigation-design。
- 与 [`evolution-design.md`](./evolution-design.md)：见 §5——模式（本文）vs 模式下的节奏（evolution-design）。

## 10. 本文的边界

本文不负责：

- 规定 `docs/DEVELOPING.md` 的逐字内容（见该文件本身）。
- 代替 `navigation-design.md` 给出入口机制条文。
- 现在就改 `evolution-design.md`（术语收编只需其中一处最小交叉引用，落地时做）。

它只负责把一件事说清楚：

> **本仓库有运行态与开发态两种模式；两态同体，故必须显式分离；而分离正是让 co-evolution 稳定的校验器边界。据此，开发态应在 `docs/` 层有独立入口。**
