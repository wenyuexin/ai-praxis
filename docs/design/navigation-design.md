# Navigation Design

本文回答：**这个仓库的“索引与查找”为什么必须是一套体系，而不是每个目录各自为政的局部规则；这套导航体系由哪几层承接，以及如何搭建、走通并校验所有链路。**

它属于 design layer：不直接替代 `docs/capabilities/navigate.md` 的能力说明，也不直接替代 `docs/contributing/rules/index-rules.md`、`readme-rules.md`、`metadata-files.md` 的执行条文。本文只处理一个更上位的问题：**为什么导航应被当作一个受治理的系统单独建模，而不是若干互不相干的 README / index 写法规定。**

## 1. 问题是什么

运行态下，`docs/` 不只是文档，它同时承载了这个仓库的规则与公共能力。一个初次上手、且**没有任何 MEMORY 记忆文件**的 AI，能否只靠仓库自身，渐进式地找到并加载到正确的规则 / 能力 / 正文？

这要求“索引与查找”具备一个性质：**体系化、规则化**——让任意协作者按同一套契约，自主学会治理文档的渐进式加载与有效查找。

当前它更接近“局部、个别”：

- README 有 README 的规则，index 有 index 的规则，`metadata-files` 定义文件模型，`navigate` 讲能力，`navigation-files` 讲设计意图——各说一段，没有单一 owner。
- 知识正文的 index 与治理文档的 index 写法不同，但这个差异没有被写成同一套契约的两个 profile，而是事实上的两种方言。
- 最关键：一个节点不会主动告诉 AI“这层不够、你多半会错、必须往深读”。下潜靠 AI 自觉，而 AI 对“不自知的误读”无法自觉。

已记录的两次失败（见 `docs/contributing/incidents/`）——capability 前置路由被跳过、overview / landscape 被当场压平——都是同一根因：**路径建了，但路标（下潜信号）和走通保证（可达性）没建。**

## 2. 一个必须先承认的物理事实：index ≠ MEMORY

工作区的 `MEMORY.md` 是 **always-loaded**（push、常驻）：它在每次会话开始就进入上下文，导航成本为零。

`index.md` 是 **load-on-demand**（pull、按需）：它不会自动进入上下文，只能作为一条**需要 AI 主动去走的路径**。

一个必须澄清的例外：根 `AGENTS.md` 在支持的 harness 里会被**自动注入**，它本身就是一个 always-loaded 单元；不注入的环境下，靠它自己的“首次必读”协议兜底。所以本仓库并非“零 MEMORY”，而是**只保留一个常驻根单元（`AGENTS.md`）+ 其余全部 pull**——这恰是想要的形态：常驻的尽量小，其余按需加载。

因此不能指望 index 像 memory 一样工作。更稳的目标不是“让 index 当 memory”，而是：

> **把 index 建成一条会在正确的点主动把读者往下按的自学习路径（self-teaching trail），让仓库在只靠一个常驻根、其余全靠 pull 的前提下仍可自导航。**

## 3. 一条 pull 型路径要逼近 memory 效果，必须补齐三件事

`MEMORY.md` 免费拥有、而 pull 型路径必须自己造出来的三个性质：

1. **保证入口**：有一个强制的起点。仓库已有——`AGENTS.md` 强制先读（写入 / 改动前再读 `CONTRIBUTING.md`）。
2. **确定性跳转**：每个节点能无歧义地把“我想要 X”指向唯一的下一跳，而不是“读了好几篇才知道哪篇适用”。
3. **节点自带下潜信号**：每个节点主动声明“这层不决定什么”以及“在对某类问题下结论前必须先加载哪篇更深文档”。

第 3 条是当前最缺的一环，也是两次失败的共同缺口。它的要害是：**下潜信号必须由系统携带，不能依赖 AI 自觉**——因为 AI 对自己不知道的误读无法自我触发下潜。

## 4. 导航节点契约

每个承担导航职责的 `README.md` / `index.md` 节点，应能提供四个字段（不是每个都长篇，而是都要被回答）：

- **定位**：这是什么地方、与相邻节点如何区分（README 主责）。
- **下行路由**：“想要 X → 去子节点 Y”，按问题 / 任务类型给出确定性单跳（index 主责）。
- **下潜触发器**：“在对 {已知易混 / 易错主题} 下结论或作答前，必须先加载 {更深文档}”，种在该误读可能发生的**最浅节点**。
- **止步线**：这一层不决定什么——提示读者当前层不足、必须继续下潜。

`overview.md` / `landscape.md` 的表面陷阱标记，就是“下潜触发器”的一个实例；本契约把它从个案升级为每个节点的常规字段。

## 5. body 与 governance：同一契约的两个 profile

知识正文目录与治理文档目录的 index 写法确有差异，但它们不是两套规则，而是同一契约的两个 profile：

- **语义型 profile（知识正文）**：下行路由按主题 / 对象语义聚类——“想看 X 概念 → 先看 Y 目录”。
- **任务型 profile（治理文档）**：下行路由按协作动作聚类——“我在做 X → 读 Y 文件”。

两个 profile 共享同样的四字段契约与同样的三条不变量（见下），只是“下行路由”的聚类轴不同。把差异显式命名为 profile，可避免它退化成无规范的方言。

## 6. 三条让“所有链路走得通”可判定的不变量

- **可达性**：每个叶子文档（rule / intent / case / incident / 正文）都能从强制入口出发，沿“下行路由”走到；不存在从任何 index 都链接不到的孤儿。
- **陷阱覆盖**：每一条 `incidents/` 记录的高频误读或已知不足，都在其最浅可发生节点种下一个下潜触发器。**这把 incident 系统直接接到导航系统**——incident 不只是历史轨迹，还是“必备下潜触发器”的来源。
- **确定性**：在同一节点，同一问题类型只指向唯一下一跳；若需要“读了才知道该不该读”，说明该节点的下行路由或下潜触发器不达标。

这三条合起来，才让“走通所有链路”从模糊愿望变成可检查的状态。

## 7. 各层承接什么（跨层接线）

导航是一个横跨多层的系统，各层职责应保持单一归属：

- `docs/capabilities/navigate.md`：**心智模型**——导航是一条会自我下潜的自学习路径；如何用 README / index 收敛范围。回答“是什么、怎么用”。
- 规则层（`index-rules.md` / `readme-rules.md`，或其上位 owner）：**可执行契约**——四字段节点契约、两个 profile、三条不变量、搭建与校验程序。回答“具体怎么写、怎么校验”。
- `docs/contributing/intent/navigation-files.md`：**为什么**——为什么 README / index / roadmap 分工、为什么 index ≠ memory、为什么局部规则不足以支撑体系化导航。
- `docs/contributing/incidents/`：**证据与触发器来源**——导航失败的轨迹，以及据此应种在表面的下潜触发器。
- 本文（design）：**架构**——为什么导航应被当作受治理的系统，以及上述各层如何拼成一条自导航链。

## 8. 如何搭建一条链路（构建程序）

新增或扩展一个节点时：

1. 在父节点 `index.md` 注册一条**下行路由**（想要 X → 来这里）。
2. 在该节点 `README.md` 写清**定位**与止步线。
3. 若该节点引入了已知易混概念，在**最浅可发生误读的节点**种一个**下潜触发器**，直指纠正文档。
4. 若该误读来自一次真实事故，先在 `incidents/` 记录，再由记录派生出对应的下潜触发器（闭合“陷阱覆盖”不变量）。

## 9. 如何走通与校验所有链路（校验程序）

定期（或在重大导航改动后）按三条不变量各跑一遍：

- **可达性检查**：枚举叶子文档，确认每个都能被至少一个 index 的下行路由链接到；找出孤儿。可部分自动化（扫描未被任何 index 引用的叶子）。
- **确定性检查**：抽查典型问题，确认每个节点上该问题类型只有一条明确下一跳，不需要“全读才知道”。
- **陷阱覆盖检查**：遍历 `incidents/` 中的误读类记录，确认每条都在最浅节点有对应下潜触发器。

三项都过，才算“所有链路走通”。任一项不过，回到第 8 节的构建程序补齐。

## 10. 本文暂不拍板、留给规则层落地时定的

- 可执行契约的 owner 落在**新建 `docs/contributing/rules/navigation-rules.md`**，还是**把 `index-rules.md` 就地升格**为该 owner。倾向前者（单一 owner，`index-rules` / `readme-rules` 降为其子细则），但迁移面需在落地时确认。
- 下潜触发器在表面文档中的统一写法（标签措辞、是否需要固定前缀）。
- 校验程序中可自动化部分的具体实现（脚本 / 人工 checklist）。

这些属于执行细则，应在设计对齐后于规则层定稿，不在本文展开。

## 11. 与其他 design 文档的边界

- 与 `system-design.md`：后者解释整个仓库为什么是一个 knowledge agent system；本文只聚焦其中的**导航 / 自导航子系统**。
- 与 `contributing-design.md`：后者解释 `docs/contributing/` 为什么继续拆成主规则 / intent / cases；本文解释这些层**如何被同一条导航链串起来并可达**。
- 与 `research-ingestion-design.md`：后者建模“材料如何被吸收进系统”（Ingest 主导）；本文建模“读者 / AI 如何找到并加载到正确文档”（Navigate 主导）。两者是输入吸收与查找定位的一对。
- 与 `../capabilities/meta.md`：后者约束能力层自身的增长；本文中凡涉及 `navigate.md` 的改动，仍应遵守其联动更新面。

## 12. 本文的边界

本文不负责：

- 规定 README / index 的逐字模板或标签措辞。
- 代替 `index-rules.md` / `readme-rules.md` / `metadata-files.md` 给出执行条文。
- 现在就决定可执行契约 owner 的最终落点（见第 10 节）。
- 提供校验脚本的具体实现。

它只负责把一件此前被当作“局部写法规定”的事说清楚：

> **索引与查找应被当作一个受治理的自导航系统：强制入口 + 确定性跳转 + 节点自带下潜信号，辅以可达性 / 陷阱覆盖 / 确定性三条不变量；它让仓库在只靠一个常驻根（`AGENTS.md`）、其余全靠 pull 的前提下仍可被渐进式、自主式地走通。**
