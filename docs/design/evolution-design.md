# Knowledge–Methodology Co-Evolution Design

本文回答：**这个仓库为什么把“积累知识”和“沉淀方法论”当成一对协同进化的过程，而不是二选一；这个循环以什么节奏运行、如何评价，以及如何在保持诚实的前提下同时吸纳实践与理论两种来源。**

它属于 design layer：不定义具体规则（那在 `docs/contributing/`），也不替代 `meta-rules.md` 的“何时改规则”。本文只处理更上位的问题：**知识与方法论这两条线为什么必须协同进化，以及什么样的进化节律与来源结构才算健康。**

## 1. 核心命题：知识与方法论的辩证关系

- **最终目的是积累知识。**
- 但知识的持续扩张需要强方法论支撑——方法论是知识持续扩张的保障。
- 知识沉淀反过来是方法论的实践与验证。
- 所以二者不是二选一，而是一个**协同进化的循环**：方法论使知识可扩张，知识生产检验并驱动方法论。

## 2. 进化节奏：日常态与开发态

**术语对齐**：本节的“日常态 / 开发态”与 [`runtime-development-design.md`](./runtime-development-design.md) 的“运行态 / 开发态”是同一对模式——**日常态即运行态**（在不修改控制面文件的前提下收集、整理知识的模式）。那篇定义两个模式*是什么*，本节只谈它们*如何交替*。

中短期内，两条线不是线性交替的。

- **日常态**：以沉淀知识为主；方法论问题**先登记**。*值不值得改*由 `meta-rules.md` §1 判定，此处只谈*何时改*——这是一次**价值 / 成本权衡**，不是固定阈值：阻塞、或继续拖延会损害当前知识工作的，立即改；改动快且几乎不打断手头工作的，可顺手改；改动成本高、或会打断正在深入的研究（研究越深，上下文切换成本越高）的，登记后到开发态集中处理。
- **开发态**：在合适的节点集中优化方法论，通常由一批已记录的问题、或一个值得深入的切入点触发。

也就是说，不是每沉淀一点知识就立刻改一次方法；方法论的成批优化被推迟到开发态集中处理。

## 3. 轮次与时间占比是重要参考，但不是充分评价尺度

单看“这段时间花在方法论还是知识上”，不能判断循环是否健康。

因为开发态本身就是批处理，天然会让某段时间集中在方法论上；而且**复杂体系的优化成本本就更高、还容易出现级联优化**（从一个问题切入，牵出更值得处理的相邻问题），因此会连续占用较多轮次。所以轮次只是一个**重要参考**，不是评价循环好坏的**充分条件**。

## 4. 局部与整体优化：价值判断引导下的选择

方法论优化类似模型训练，但**关键差异在于价值判断**：训练只跟随 loss、没有价值判断；而人或部分高阶 AI 能区分问题的**性质与重要性**。

因此“走局部还是整体”本身是一次价值判断，而不是盲目跟随最陡梯度：

- **整体优化**解决系统性问题；**快速局部优化**在局部问题上迭代更快。
- 一次有效的整体优化，在系统性问题上可能胜过许多精细局部优化；但不能反推成“整体永远优于局部”——两者**场景依赖、各有其位**。
- 复杂体系里还有**关联 / 级联现象**：从一个问题切入，常会发现更值得关注的相邻问题；是否顺着级联走下去，同样由价值判断决定。

## 5. 方法论的两个合法来源：实践与理论的辩证

方法论进化有两个并列互补的来源，不是一个合法、一个可疑：

- **自底向上（实践）**：在沉淀知识的过程中找出优化点——从本仓库自身的知识生产中归纳出方法论改进。
- **自顶向下（理论）**：依据先验知识（成熟的理论化研究、他人成熟的实践方案等间接经验）与人的主观理解做逻辑推导，而非从自身知识沉淀中归纳。尤其在有人类或高阶模型的价值判断参与时，它同样重要、有时必要——因为自底向上沉淀几千篇也未必能归纳出高抽象的治理规则；有些高抽象原则只能先靠推导到达，再自顶向下展开设计。

这是**实践与理论的辩证**（“理论”取实践论意义上的理性认识 / 间接经验，不限于学术理论；底层机制即归纳与演绎）：纯归纳未必够得着高抽象，纯推导又可能脱离现实，两条腿都要。

## 6. 诚实性保险：标注来源，但不贬低理论

（操作性建议）无论来自实践还是理论，方法论主张都**可以**沿用 evidence 分级标注（`Observed` / `Inferred`）；判定口径以 [`evidence-assessment-rules.md`](../contributing/rules/evidence-assessment-rules.md) 为准，本文不另给定义。

这个标注**不是为了贬低自顶向下推导**，而是为了知道“什么已被实践检验、什么还是待验证的理论预测”；标注只反映验证状态，不改变规则本身的约束力。自顶向下推出的原则像一条理论预测，后续由实践确认或证伪——这正是把它接回协同进化循环的方式。

## 7. 这套理念如何落在系统机制里

它不是新增机制，而是把已有机制统一理解成一个循环：

- **自底向上那条腿已有齿轮**：`incidents/` 记录真实摩擦，`meta-rules.md` §1 的复发 / 直接观察 / 高危维度触发，把实践问题回沉成规则。
- **自顶向下那条腿由 design layer 承接**：本文与 `system-design.md` 等承接理论推导出的高抽象原则，再向 rules / capabilities 展开。
- **证据分级**（`Verified` / `Observed` / `Inferred` / …）天然是第 6 节“诚实性保险”的载体。

## 8. 与其他 design 文档的边界

- 与 `system-design.md`：后者讲系统的**静态**分层与组成；本文讲这套系统随时间如何**协同进化**（动态维度）。
- 与 `meta-rules.md`（rules 层）：后者是“何时 / 如何改规则”的可执行触发；本文是它背后的进化哲学——为什么改规则要锚在真实摩擦，或经价值判断的理论推导上。
- 与 `research-ingestion-design.md` / `navigation-design.md`：那些是具体子系统的专项设计；本文是贯穿各子系统演化的上位模型。

## 9. 本文的边界

本文不负责：

- 规定改规则的具体触发条件与流程（见 `meta-rules.md`）。
- 定义 Evidence 状态的判定细则（见 evidence 相关规则）。
- 给出知识域的具体建设计划。
- 把日常态 / 开发态的切换硬性成规——那是一次价值判断，不宜固化成阈值。

它只负责把一件根本性的事说清楚：

> **积累知识是目的，方法论是保障，知识沉淀是方法论的实践与验证，二者协同进化。这个循环既由自底向上的真实摩擦驱动，也由自顶向下、经价值判断的理论推导驱动；两种来源的验证状态宜诚实标注，但都不可偏废。**
