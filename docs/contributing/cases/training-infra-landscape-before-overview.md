# Training Infrastructure：`landscape.md` 先于 `overview.md` 出现的案例

> **历史案例（B+C 生效前）**：本文记录旧规则下的 `landscape.md` 结构支架模型，不再作为当前文件创建建议。当前规则见 [`../rules/metadata-files.md`](../rules/metadata-files.md) 与 [`../rules/research-artifacts.md`](../rules/research-artifacts.md)：稳定部分优先回流既有 owner，只有满足 C 条件时才创建非固定命名的结构研究辅助材料。

本历史案例用于说明：**在旧规则下，当一个目录最先稳定出现的是结构切分、边界归属与研究下钻路径，而不是人类向主线判断时，为什么当时曾把材料落在 `README.md`、`index.md`、`landscape.md`、`roadmap.md`，并暂不创建 `overview.md`。** 当前不再据此创建固定的 `landscape.md`；类似结构判断应按 B+C 规则重新分流。

## 1. 这个案例回答什么问题

它回答的不是训练基础设施本身的知识细节，而是下面这些规则判断：

- 旧规则下什么情况下 `landscape.md` 曾先于 `overview.md` 出现
- 为什么“当前没有 `overview.md`”有时不是缺文件，而是时机尚未成熟
- 为什么旧规则下一个目录曾同时需要 `index.md`、`landscape.md`、`roadmap.md`，但这并不等于职责重叠
- 为什么 README 即使仍然很重要，也不该继续扛目录树、路径和结构治理

## 2. 案例背景

`training-infra/` 关注的是大规模模型训练过程中的工程底座。

这个目录天然会遇到几类很重的结构问题：

- 主题可以按系统层、瓶颈类型、生命周期阶段等多种轴切分
- 与 `llm/`、`deep-learning/`、`reinforce-learning/` 的边界并不天然自明
- 继续补材料时，维护者首先会问“这应落在哪一层、与哪个相邻目录分工”，而不是“这能否先写成一篇主文”

也就是说，这个目录最先暴露出来的不是主线综述需求，而是**结构支架需求**。

## 3. 为什么这里不应急着写 `overview.md`

按主规则，`overview.md` 只有在目录已经积累出足以支撑一篇相对独立、可单篇成立的人类向主文时才应出现。

而这个目录当前并不满足这个条件：

- 各主干子目录虽然已经稳定，但内容仍在继续建设
- 读者当前最先需要恢复的，不是单一主线叙事，而是“这个主题内部如何切、与相邻目录怎么分工”
- 如果此时急着写 `overview.md`，很容易把结构治理、边界裁剪和主线理解混进同一篇文档里

所以旧规则下更稳的判断不是“补齐文件类型”，而是承认：**当时更早成熟的是 `landscape` 信号，不是 `overview` 信号。** 在当前 B+C 模型下，这个判断保留为历史经验，不再自动推出创建 `landscape.md`。

## 4. 旧规则下本案例采用的拆分方式

在当时的规则语境下，对 `training-infra/` 采用的拆分是：

- `README.md`：保留目录定位、轻量分类依据、边界说明与最小入口分流
- `index.md`：承接目录结构、按子目录定位、按问题找入口
- `landscape.md`：承接为什么这样切分、与相邻目录如何分工、后续该往哪里下钻
- `roadmap.md`：承接按读者背景推荐起点、学习顺序与推进路径
- 暂不创建 `overview.md`

这里历史上最关键的不是“多建几个元信息文件”，而是把几类不同认知任务拆开。当前规则仍保留这种职责区分，但不再把 `landscape.md` 作为固定承载位：

- 目录说明
- 结构与查找
- 结构支架与边界治理
- 起点与路径

## 5. 这个案例最容易诱发的三类误判

### 误判 A：训练基础设施主题很大，所以应该先写 `overview.md`

这种误判会忽略一个关键条件：主题大，不等于已经形成单篇可成立的人类向主文。这个历史案例并不表示当前应先创建 `landscape.md`。

如果结构切分、边界归属与下钻路径还在频繁影响材料落位，`overview.md` 往往还不是最先该出现的文件。

### 误判 B：既然已经有 `landscape.md`，那 `index.md` 可以不建

这种历史误判会把“结构支架”与“目录导航”混为一谈。当前结构判断应先按 B+C 规则寻找既有 owner。

- `landscape.md` 解释为什么这样切、各部分如何分工
- `index.md` 解决我已经知道想找什么时该去哪

两者都可能需要，但它们回答的不是同一类问题。

### 误判 C：既然 README 里已经说明了分类依据，`landscape.md` 只是重复

这种历史误判会低估“轻量分类依据”和“结构化研究文”的差异。

README 只需要让读者先判断这个目录是否相关；`landscape.md` 则需要稳定回答：

- 为什么按这一轴切，而不是按另一轴切
- 与相邻目录如何分工
- 补新材料时应优先按什么结构继续下钻

## 6. 这个案例给出的关键判断

这个案例作为历史材料仍值得复用的判断有四条，但不再把固定文件名当作当前建议：

- 结构研究需求不一定从 `overview.md` 里拆出来；在旧规则下它曾先以 `landscape.md` 研究支架出现，当前则按 B+C 判断非固定命名的辅助材料
- 当结构问题先成熟时，“暂时没有 `overview.md`”是合理状态，不是缺文件
- 旧规则下 `README.md`、`index.md`、`landscape.md`、`roadmap.md` 可以同时存在，但前提是它们回答的认知任务不同
- 目录越容易在 README 中混进目录树、路径和结构治理，越要尽早把这些职责拆出去

### 6.1 旧模型保留的具体取舍依据

以下两组判断属于当时的历史模型证据，不是当前 `training-infra/` 的新增规则：

- 旧模型选择按工程瓶颈与系统层切分，而不是按模型家族、论文流派或训练阶段重排，主要因为训练系统的约束横跨计算、通信、显存、编译、运维和可观测性等层面；同一种训练方法也可能跨越多类基础设施问题，按方法论重切容易与 `llm/03-training/` 重叠；维护者补材料时也更常先面对“这属于哪类工程约束”，而不是“这是否已经能写成一篇总览主文”。
- 旧模型曾使用这样的落位启发式：如果问题是在问“这种训练方法是什么、为什么这样训练”，优先回到模型或训练目录；如果问题是在问“这种训练方法如何在算力、框架、显存和运维条件下跑起来”，则留在 `training-infra/`。

这些判断只用于恢复旧模型为什么这样组织的历史语境；当前新增材料仍须按现行 README、index、roadmap 和 C 规则重新判断。

## 7. 什么情况下应重新触发 `overview.md` 判断

如果未来出现下面任一情况，应重新评估是否在 `training-infra/` 补 `overview.md`：

- 顶层已经形成稳定主线，且读者只读一篇就应先读它
- 多个子目录的问题开始反复回到同一组上位判断
- 当时仅靠 README、index、landscape、roadmap，读者仍无法恢复整体理解
- 目录已经积累出足以支撑相对独立人类向主文的材料与主线判断

也就是说，本案例不是在证明“`training-infra/` 永远不需要 `overview.md`”，而是在说明：**当时的时点还不该机械创建它。** 当前是否需要 overview，按现行规则判断。

## 8. 这个案例对规则系统的直接启发

本案例的核心价值，不是重复主规则或 `intent/` 中已经给出的时机模型，而是提供一个可观察的真实样本，说明“结构支架先成熟”在仓库里曾长成什么样。当前相关结论应回到 `docs/contributing/rules/metadata-files.md` §2 / §4.4、`docs/contributing/rules/research-artifacts.md` §5.2，以及 `docs/contributing/intent/metadata-files.md` §10 / §12 统一理解。

它对应的是一种很典型的研究建设流程：

1. 先有目录定位
2. 然后结构问题先暴露
3. 再把目录导航与学习路径从 README 中拆出去
4. 最后才在材料成熟后考虑 `overview.md`

这条历史过程仍可作为判断顺序参考，但当前结构研究材料必须先经过 C 条件判断，不得直接恢复 `landscape.md` 固定类型。

## 9. 什么时候才该回看这个案例

只有在以下情况才需要回看本案例：

- 已经读过主规则，但仍拿不准“为什么这里允许先有 `landscape.md` 而没有 `overview.md`”
- 需要判断某个目录是不是已经暴露出结构支架问题，而不是主线主文问题
- 需要复盘为什么某些目录不该急着补 `overview.md`
- 需要给其他 AI 一个真实样本，说明 `landscape-before-overview` 不是纸上规则

如果只是日常判断元信息文件职责，优先回到 `docs/contributing/rules/metadata-files.md`；如果只是想理解这些职责为什么这样定义，再优先回到 `docs/contributing/intent/metadata-files.md`。
