# Incident: 按“改哪个文件”反推运行态 / 开发态，导致模式误判

- 当前状态：Active
- 是否复发：已复发（同一会话内 2 次）
- 记录日期：2026-09-18
- 触发类别：§1 复发 + 高危维度 · 静默失败 / 高影响面

## 问题背景

一次会话中，用户让 AI 看 `docs/DEVELOPING.md` 并评估现有 docs 体系是否足够支撑某研究主题（deepseek-harness）。AI 用“这次改 / 评的是控制面还是数据面文件”来判断自己处于哪个模式：先在未加载开发态治理（`DEVELOPING.md` → `meta-rules.md` → `design/`）的情况下，对控制面下了结论（判“框架缺口”、提规则修改、找外部方案借鉴）；被纠正后又把自己的越界描述成“从运行态滑进开发态”，仍是以文件反推模式。

## 冲突点

`runtime-development-design.md` §2 明确：运行态 / 开发态（生命周期 / 模式轴）与 控制面 / 数据面（文件角色轴）是两条不同的轴，不能等价。但实际执行把“改哪个面的文件”当成了模式判据，即用文件面反推模式。这带来两个错误：

- 开发态其实可以**先于任何文件改动**存在（评估 / 推敲控制面是否该改就已是开发态），文件判据会把这段误判成运行态——这正是本次 AI 在未走路由时就产出控制面结论的根因。
- 为验证控制面改动而做的数据面知识沉淀，会被文件判据误判成“切回运行态”。

此外 §4 的 2×2 把“开发态 × 数据面”写成“少见，只在大规模迁移时发生”，未涵盖“验证性知识沉淀”这一常见居民，间接助长了上述反推。

## 危害场景（§1 高危维度要求的具体场景陈述）

- 频繁穿插修改（一边改控制面、一边改数据面）时，按文件反推会造成模式高频翻转，AI 难以稳定自判；控制面误判可污染下游且不易立刻暴露（静默失败）。
- 开发态意图在“尚未落笔改文件”时不被识别 → 控制面评估 / 结论在缺少 `meta-rules.md` §1 触发与人类签核的情况下产出。

## 解决方案

- 已改（本次落地）：`runtime-development-design.md` §4 明确“模式按主导意图判定、不按当前文件面判定”，补两个推论（开发态可先于文件改动；开发态循环可同时跨两面），并把“开发态 × 数据面”扩写为包含“为验证控制面改动而做的知识沉淀”；§5 的运行态定义补“不改造 / 评判控制面”的意图前提。
- 已改（本次落地）：`DEVELOPING.md` §1 判据从“会不会改控制面文件”改为“主导意图是否在作者化或评判控制面”（覆盖“还没落笔改文件”的评估情形），并就地对齐同文件 §3 头部、§36 止步线、§10 贡献知识分类。
- 不变前提：校验器边界仍靠文件面守闸——控制面编辑独立要过 `meta-rules.md` §1 触发 + §3 签核，与模式标签无关（`runtime-development-design.md` §7）。
- 待定（未改，留待维护者判断）：“改控制面 = 开发态”的窄措辞仍存于 `AGENTS.md` §2（根入口、影响面最大）、`docs/capabilities/navigate.md`、`docs/README.md`、`CONTRIBUTING.md`、`evolution-design.md` §2，是否统一对齐成“改或评判”，单独判断。
- 状态说明：改动尚未提交、上述对齐待定、且行为刚复发，故保持 `Active`；相关条文稳定合入后再转 `Resolved`。
