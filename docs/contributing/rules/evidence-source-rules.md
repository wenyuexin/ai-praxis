# Evidence 来源边界规则

本文件回答：**不同材料类型分别能支持什么，不能外推什么，以及需要进入哪类专属判断路径？**

通用 Claim 与 Evidence Status 见 [`evidence-assessment-rules.md`](./evidence-assessment-rules.md)；记录位置和呈现格式见 [`evidence-recording-rules.md`](./evidence-recording-rules.md)；组合流程见 [`evidence-and-traceability.md`](./evidence-and-traceability.md)。

## 1. 来源类型总览

| 来源类型 | 默认强度 | 可支持的内容 | 注意事项 |
|---|---|---|---|
| 论文原文 | 高 | 方法、实验、定义、理论主张 | 不要把单篇论文外推成领域共识 |
| 官方文档 | 高 | 功能、接口、版本行为、设计意图 | 注意版本和发布日期 |
| 源码 | 高 | 具体版本上的实际实现与工程行为 | 版本可追溯的直接源码观察标为 `Observed`；注意 commit、tag、分支与观察时间 |
| release notes | 高 | 已发布的实现行为或版本变更声明 | 注意版本和发布日期；明确声明可按直接证据判断为 `Verified` |
| issue / PR | 中 | 设计讨论、问题背景、维护者解释 | 区分正式结论和讨论过程 |
| benchmark / 实验报告 | 中到高 | 评测结果、任务定义、指标 | 注意实验设置和适用范围 |
| 技术博客 / 社区讨论 | 中到低 | 趋势、痛点、经验观察 | 不直接支持强事实定论 |
| 仓库内已有文档 / 用户调研上下文 | 中 | 本仓库上下文、已有分类、建设方向和用户需求 | 要区分仓库约束、用户上下文与领域知识 |
| AI / 作者综合判断 | 低 | 结构草稿、初步分类、待验证假设 | 默认标为 `Inferred` 或 `Unverified` |

默认强度不是最终 Status。仍需根据 Claim 是否被来源直接支撑、观察对象和适用范围作出判断。

## 2. 论文与正式研究文献

- 论文原文可以直接支持作者明确写出的定义、方法、实验设置、报告结果和限定范围内的结论。
- 单篇论文不能直接外推为领域共识、行业主流或普遍工程最佳实践。
- 论文没有明确说明的实现细节、API 行为、调度细节、token 语义或工程流程，不得补写成论文结论。
- 读者根据论文事实形成的解释应标为解释性推论；教学例子、可选实现和反事实必须与原文实际流程区分。
- 实验结果必须保留必要的任务、数据、指标和设置边界；结果的组织方式见 [`research-artifacts.md`](./research-artifacts.md)。

## 3. 代码库、源码与 release notes

### 3.1 Claim 级源码边界

- 版本可追溯的直接源码观察标为 `Observed`，不得写成无版本边界的长期定论；官方 release notes 对实现行为或版本变化的明确声明仍可按直接证据判断为 `Verified`。
- Claim 应明确观察对象的 `branch`、`tag/release` 或 `commit` 范围；不同分支、版本窗口或 release notes 不得在没有边界说明时拼成一个结论。
- Claim 依赖当前源码实现时，优先记录可还原的具体 `commit`；只有明确描述已发布版本时，才优先使用 `tag/release`。
- 只观察默认分支、feature branch、实验目录或未发布 PR 时，不得将该能力写成项目总体能力；issue / PR 中讨论的未来功能也不得写成当前实现。

### 3.2 版本链路字段

版本链路字段由 [`traceability-rules.md`](./traceability-rules.md) §3.5 承接。本文件只规定源码观察对 Claim 状态和正文表达的约束。

只要结论基于源码观察，至少需要能够补齐 `Version Basis` 和 `Observed At`；适用范围和迭代风险按 Traceability 规则按需补充。

### 3.3 缺少版本信息时

基于源码的 Claim 缺少 `Version Basis` 或 `Observed At` 时，先判断被观察版本能否可复现地找回：

- 能找回时，补齐版本、观察时间和适用范围，并按 `Observed` 重新标注后再保留该 Claim。
- 不能找回时，不得保留为稳定正文，只能作为 `Unverified` 线索留在 `temp/`，或将待核验缺口写入 `backlog.md`。

## 4. Benchmark 与实验报告

- Benchmark 或实验报告可以支持报告范围内的任务定义、指标、实验结果和比较结论。
- 不同数据集、指标、样本、基线或运行条件下的结果，不得在没有设置说明时直接横向比较。
- 单次实验结果不得直接写成稳定趋势、普遍规律或显著性结论；是否存在统计支持取决于报告实际提供的实验信息。
- “报告中声称的结果”和“本地复现得到的结果”必须区分；复现环境、版本和偏差属于研究产物与 Trace 的记录范围。
- 实验设置、指标和辅助材料的组织方式见 [`research-artifacts.md`](./research-artifacts.md)，不在本文件重复定义研究产物结构。

## 5. Issue、PR、博客与社区讨论

- issue / PR 可以支持设计讨论、问题背景、维护者解释和未来方向，但必须区分正式结论与讨论过程。
- 未合并 PR、未来 issue 或讨论中的计划不得写成当前实现或稳定能力。
- 技术博客和社区讨论适合支持趋势、痛点和经验观察，不直接支持强事实定论。
- AI 或作者综合判断默认标为 `Inferred` 或 `Unverified`；不要把综合整理伪装成来源直接结论。
