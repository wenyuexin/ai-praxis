# Evidence 来源边界设计意图

本文件解释为什么不同材料类型需要不同的来源边界，以及为什么这些边界不能被简化成来源强度排名。

## 1. 来源类型不是 Evidence Status

“论文”“源码”“实验报告”描述材料类型；`Verified`、`Observed`、`Inferred` 等描述当前 Claim 与材料之间的支持关系。

同一种材料可能支持不同状态：

- 论文原文对作者明确写出的结果可以是 `Verified`；读者基于多段内容形成的分类可能是 `Inferred`。
- 版本可追溯的直接源码观察是 `Observed`；官方 release notes 对已发布行为的明确声明可以是 `Verified`。
- 实验报告中的结果可以被原文直接报告，但不能因此自动成为普遍规律。

因此来源类型规则只能提供判断边界，不能替代通用 Status 模型。

## 2. 为什么代码库需要更强的边界

源码实现天然带有版本和时间截面。只看默认分支、feature branch 或实验目录，不能推出项目整体的长期能力。

`Version Basis` 和 `Observed At` 的字段定义属于 Traceability；源码 Claim 能否写成当前能力、应标什么状态，则属于 Evidence 来源边界。两层必须协同，但不能互相复制。

## 3. 为什么论文和实验报告暂不各自拆文件

论文研究确实容易混写来源事实、解释性推论、未确认实现和教学例子；实验报告也需要保留实验设置和适用范围。但这些风险目前可以由通用高风险 Claim 规则、来源总览和研究产物规则共同承接。

如果未来某类材料形成独立 stop-line，应先确认：

- 它是否无法由通用 Claim / Status 规则表达；
- 它是否无法由 `research-artifacts.md` 或 `traceability-rules.md` 承接；
- 独立文件是否会减少目标任务的阅读和误判成本。

只有满足这些条件，才从 `evidence-source-rules.md` 继续拆出材料类型文件。

## 4. 为什么不能只按来源强度排序

来源强度只能提供初始参照，不能决定 Claim 的最终状态。论文可能只支持一个受限实验结论，源码可能只说明某个 commit 的局部行为，博客可能包含准确但未充分验证的观察。

最终判断仍必须同时看：

- Claim 是否被来源直接支撑；
- 观察对象和适用范围；
- 是否存在版本、设置或定义边界；
- 是否把来源未覆盖的外推写进了 Claim。

## 5. 来源规则的长期增长方式

来源类型模块是按需增长的边界容器，不是要求所有来源类型一开始都拥有独立文件的模板。

未来新增来源类型时，优先在本文件中增加一个短小节；只有当该小节持续增长、出现稳定误判并形成独立执行路径时，才考虑拆出新规则文件。
