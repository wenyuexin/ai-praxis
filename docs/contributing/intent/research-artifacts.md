# 研究产物组织规则的设计意图

本文件不重复 `../rules/research-artifacts.md` 的条文，而是解释：**为什么研究单元不能只按“主题 / 对象”二分，以及为什么有些高价值对象必须按“主题+对象混合型”处理。**

## 1. 这个文件回答什么问题

`research-artifacts.md` 负责回答：研究产物怎么组织、子领域研究和具体案例研究怎么分、正文和辅助材料怎么分层。

本文件回答的是更上游的问题：

- 为什么“主题”和“对象”不足以覆盖所有高价值研究单元
- 为什么有些具体对象同时承载一个重要想法，不能被压扁成纯对象案例
- 为什么“高研究价值”不自动推出“应该留在当前主题树里”
- 为什么混合型单元需要单独的研究方法，而不是在主题研究和对象研究之间随意折中
- 为什么持续演进的版本对象不能被当成静态对象处理，以及这会如何反过来影响目录级总览、对象正文和 `report` 命名

## 2. 为什么二分法会稳定误判

“主题 / 对象”二分在多数情况下是够用的，但它有一个稳定盲点：

- 有些想法非常重要
- 它们能代表一种新范式、方法原型或结构信号
- 但它们可能基础、简单，或者尚未被广泛接受
- 结果就是：开源生态中直接围绕这个想法展开的项目不多

这时如果还强行二分，AI 很容易犯两种错：

- 因为它是具体项目，就把它降格成纯对象，不再讨论它背后的方法代表性
- 因为它背后有重要想法，就把它抬成纯主题，好像它已经有稳定的对象簇和成熟赛道

这两种理解都会丢掉真实情况。

因此，第三类不能被当成“暂时不好归类时的兜底桶”。对象很重要、资料很多、或者当前一时不好落位，都不自动构成混合型的触发条件；只有当“对象本身同时承担一个重要想法的主要研究入口”时，才应进入这一类。

## 3. 为什么需要“主题+对象混合型”

有些研究单元的真实状态是：

- 研究入口是一个具体对象
- 但研究价值不只在对象本体
- 它同时还是某个重要想法最清晰、最高信号的载体

这时它既不是纯主题，也不是纯对象。

引入“主题+对象混合型”，不是为了增加分类花样，而是为了保留一个真实存在的研究状态：**一个具体对象本身就是某个重要想法的主要研究入口。**

## 4. 这类单元最容易被误解成什么

AI 最容易把这类单元误读成下面两种极端：

- “既然是具体项目，那就是普通对象研究。”
- “既然它代表一个想法，那就应该和成熟主题目录并列。”

前者的问题是：会把对象研究写成仓库说明书，丢掉它的范式信号。

后者的问题是：会假装这个想法已经形成成熟主题生态，导致目录落位、文档职责和比较基线全部失真。

## 5. 为什么“高研究价值”与“当前落位正确”是两回事

高研究价值只能说明：

- 值得投入研究
- 值得单独建研究单元
- 值得按长期主义看待，不因当前材料少而低估它

但它不能自动说明：

- 应该和当前主题树中的主题目录并列
- 应该按主题综述方法去组织
- 应该被看作同层分类轴上的同类节点

也就是说：

- **研究价值**回答“要不要深入研究它”
- **分类轴一致性**回答“它应不应该放在这里”

把这两个问题混为一谈，会稳定导致“因为对象很重要，所以把它硬塞进最相关主题树里”。

而“和某主题很相关”也不是继续挂靠在该主题树下的充分理由。如果挂靠之后，它会稳定被误读成同层主题目录，那么这种误读成本本身就是否决条件，优先级高于表面的主题相关性。

## 6. 混合型单元的研究方法为什么必须单独写

纯主题和纯对象的研究方法都不适合直接套到混合型单元上。

- 如果按纯主题写，会过早抽象，假装已有大量对象可以横向比较。
- 如果按纯对象写，会只剩对象本体解剖，失去它作为方法入口的价值。

所以混合型单元的主文必须同时回答两件事：

- 这个对象本体是什么
- 它为什么足以成为某个更大想法的代表性入口

同时还要明确写出一句“不等于”：

- 这个对象能承载该想法，**不等于**该想法已经形成成熟对象生态

## 7. 混合型单元为什么容易把目录结构带偏

如果不给它单独规则，混合型单元会稳定把目录结构往两个方向带偏：

- 要么在主题树里越写越像对象研究目录
- 要么在对象目录里彻底失去方法代表性，只剩实现细节

所以这类单元的真正风险不是“写不深”，而是**写着写着改变了周围目录的分类语义**。

这也是为什么主规则里必须先判断研究单元类型，再判断落位，而不是反过来先看它像不像某个现成目录。

## 8. 一个典型误读信号

当 AI 开始说出下面这类话时，通常说明它已经偏离了这条规则的原意：

- “它就是一个项目，所以按对象研究就行……”
- “它代表一个想法，所以应该当成主题目录……”
- “既然研究价值高，那就直接留在最相关主题树……”

这些说法的问题分别是：

- 忽略了对象背后的方法代表性
- 假装想法已经拥有成熟主题生态
- 把研究价值和落位判断混成一个问题

## 8.1 为什么持续演进对象不能直接借用 `overview` 或泛化 `report`

有些研究对象并不是一个稳定不变的单体，而是一条持续演进的版本链，例如：

- 商业 / 公开模型的 `5.0 / 5.1 / 5.2`
- 持续发布的模型权重与服务变体
- 同一系列下共享技术背景、但版本能力边界明显不同的对象

这类对象最容易诱发两种误判：

- 因为某个版本文承担“快速理解”功能，就把它命名成 `*-overview.md`
- 因为研究入口来自官方 technical report / system card / blog，就把所有版本对象文都泛化成 `*-report.md`

这两种做法都会丢掉一个更重要的事实：**版本边界本身就是对象语义的一部分。**

更稳的理解方式是：

- 目录级 `overview.md` 回答“这个系列怎么分、版本关系是什么、该先读哪篇”
- 版本对象正文回答“这一版对象本身是什么、当前公开形态如何、哪些结论只属于这一版”
- `*-report.md` 只在文档主对象明确是某份上游 report / technical report / system card / whitepaper 时使用，而不是因为它看起来更正式

也就是说：

- `overview` 是目录级槽位名，不是“任何快速理解文”都可借用的普通后缀
- `report` 是来源驱动命名，不是“研究文看起来更完整”时就默认采用的通用名字
- 当文档承接的是版本对象本身，而不是单一上游报告时，最稳的命名通常仍是带版本标识的对象文件名

## 9. 为什么 notes 目录采用二态容器

`research-artifacts.md` 的 §3.3、§3.7、§3.9、§5、§7 共同定义了一个更容易执行的二态判断：对象要么不需要独立辅助材料，要么需要独立辅助材料并从第一篇材料开始使用 `notes/`。这里的关键不是材料数量，而是是否已经出现独立于正文的对象级研究过程。

- **无独立辅助层**：如果过程材料仍适合贴着正文理解、不需要独立维护，就不创建 `notes/`；可保留在正文或专题文件的局部 `## Research Notes` 中。
- **有独立辅助层**：一旦材料需要脱离正文单独维护，就从第一篇材料开始放入对象目录的 `notes/`，不再先创建根目录 `notes.md`、`source-notes.md`、`evidence-notes.md` 或 `reflections.md` 再等待升级。
- **不预建空模板**：`notes/` 可以只有一个实际文件；首文件按材料类型、机制或来源命名，不强制叫 `general.md`。`general.md` 只是承接未进一步分类的过程材料的可选名称。
- **开放命名而非固定四件套**：`source.md`、`evidence.md`、`reflections.md` 以及 `<mechanism>.md`、`<source-name>.md` 都是可用命名，但只在对应内容真实存在时创建。

这种二态设计删除的是“少 / 中 / 多”之间没有可执行阈值的容器切换，不删除正文内部的局部研究记录，也不要求把所有辅助材料拆成固定文件集合。

更大的“构造辅助层家族”视角（`temp/` / `notes/` / 元信息文件如何统一分工），见 [`../../design/auxiliary-layers-design.md`](../../design/auxiliary-layers-design.md)（初稿）。

## 9.1 研究辅助层是上位概念

“研究辅助材料”描述的是材料在研究过程中的治理作用，不预设单一物理容器。对象研究时，它特化为对象目录下的 `notes/`；研究多个文档或目录的结构判断时，它可以在 C 的严格条件下形成结构研究辅助材料；其他作用域则按实际任务判断，不因目录范围扩大就机械创建根 `notes/`。

这一区分很重要：

- 对象 `notes/` 承接对象归属已经稳定、但正文尚未足够成熟的研究过程材料；
- C 的结构研究辅助材料承接尚未稳定、影响多个并列文档或目录、且既有 owner 无法承接的结构判断；
- 二者都必须在稳定后回流到既有 owner；
- C 不是第四个固定层，不是 `notes/landscape.md`，也不替代 `plan.md`、`roadmap.md` 或 `overview.md`。

具体运行规则由 [`../rules/research-artifacts.md §3.3、§5.2`](../rules/research-artifacts.md) 承担，本节只解释上下位关系。

## 10. 主规则应该保留什么，`intent/` 再补什么

主规则文件里，应该保留足够短、足够稳的内容，例如：

- 研究单元先分主题、对象、主题+对象混合型三类
- 不要把所有高价值研究单元都压成“主题”或“对象”二选一
- 高研究价值不等于必然留在当前主题树
- 混合型单元允许挂靠主题目录，但必须明确它是代表性对象入口，不是同层通用主题

这些信息应该足以让 AI 在多数场景下先执行对。

而 `intent/research-artifacts.md` 补的是：

- 为什么会出现“重要但对象稀少”的想法型研究单元
- 为什么二分法在这类问题上会稳定误判
- 为什么混合型单元既不能写成纯对象说明书，也不能假装是成熟主题综述
- 为什么研究价值和落位判断必须拆开看
- 为什么持续演进的版本对象需要把目录级总览、版本对象正文和上游 report 整理文分开命名
- 为什么 notes 目录采用“无独立辅助层 / 有独立辅助层”二态，而不是按材料体量在平铺文件与目录之间切换
- 为什么一般研究辅助层是上位概念，对象 `notes/` 和结构研究辅助材料是不同作用域的特化

## 11. 本文件的使用方式

本文件不是默认入口。

只有在以下情况才读：

- 需要修改 `research-artifacts.md`
- 发现 AI 在“主题 / 对象”判断上反复摇摆
- 需要解释某个高价值对象为什么既不像纯主题，也不像纯对象
- 需要讨论“该不该留在当前主题树里”这类落位争议
- 需要解释 notes 目录为什么采用二态容器、类型为什么不是封闭枚举

平时执行研究组织任务，仍优先读 `research-artifacts.md` 本身。
