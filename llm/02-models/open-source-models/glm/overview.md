# GLM 系列总览

本篇是 GLM / `GLM-5.x` 系列的人类向总览主文。它不替代具体版本对象文，也不展开完整技术报告细节；它只回答一个问题：如果只读一篇，应该先怎样理解这一代 GLM 系列的主线。

## 一、系列主线：从代码生成到长程工程执行

当前 `GLM-5.x` 最值得先抓住的不是“又一个代码模型版本”，而是它把模型定位从单次代码生成推进到更长程的 `agentic engineering`。

在这个语境里，coding 不只是生成一段函数或修一个局部 bug，而是更接近持续执行的工程任务：模型需要读入较长项目上下文，保持目录结构、模块边界、接口契约和历史决策，在多步骤中调用工具、改动代码、检查反馈并继续推进。

因此，`GLM-5.x` 的核心理解线索可以压缩成几组关系：

- **任务形态**：从短交互、单次生成，转向长链路、多步骤、带约束保持的工程执行
- **能力支撑**：长上下文、工具调用、结构化输出、上下文缓存和长输出能力共同服务于 agent workflow
- **技术背景**：大规模 MoE、DSA / sparse attention、长上下文效率优化等，是理解这一代路线的重要背景
- **发布形态**：系列不只由论文或单一仓库承接，而是由 technical report、官方博客、产品文档、模型页、系列仓库和权重发布页共同构成

## 二、GLM-5 在系列中的角色

`GLM-5` 是当前公开技术报告最直接承接的版本节点。报告标题 `GLM-5: from Vibe Coding to Agentic Engineering` 已经把这一代路线放在从 `vibe coding` 到 `agentic engineering` 的转向里。

这使得 `GLM-5` 在系列里承担两层角色：

- 它是一个具体版本对象，需要按 `GLM-5` 自身的公开材料和版本边界来研究
- 它也是后续 `GLM-5.1`、`GLM-5.2` 经常回引的系列技术背景，提供理解后续版本的路线锚点

这两层不能混在一起。`GLM-5` 报告可以帮助理解系列为何重视 long-horizon task、coding、tool-use、MoE 与 sparse attention，但报告中的训练细节、参数规模和 benchmark 不能自动外推为 `GLM-5.1` 或 `GLM-5.2` 的独立事实。

## 三、版本演进的高层理解

从当前已整理的公开材料看，`GLM-5.x` 的演进可以先按三步理解：

1. `GLM-5` 建立系列技术锚点，把路线从 `vibe coding` 明确推向 `agentic engineering`
2. `GLM-5.1` 沿主架构继续推进，把长程任务执行、agent workflow 和开放权重发布形态变成更清晰的版本对象身份
3. `GLM-5.2` 将这一方向进一步推到 `1M` 上下文、项目级工程执行和更明确的架构级增量

这条演进线说明，`GLM-5.x` 不是简单的“版本号递增”。后续版本持续强化的是长上下文下的任务保持、跨文件工程执行、工具工作流接入，以及面向部署和开放权重的发布承接。

更详细的版本差异、连续继承项和明显升级项，见 [`glm-5.x-evolution.md`](./glm-5.x-evolution.md)。

## 四、当前可稳定保留的判断

基于现有版本对象文和公开材料，当前较稳的系列级判断包括：

- `GLM-5.x` 应优先放在 `agentic engineering` 和 long-horizon task 语境中理解，而不是只按聊天模型或代码补全模型理解
- `GLM-5` 是报告承接最直接的基础版本节点，也是系列技术背景的主要来源
- `GLM-5.1`、`GLM-5.2` 当前更适合按独立版本对象处理，不应被压成 `GLM-5` 报告的附属段落
- `200K` 到 `1M` 的上下文提升，不只是窗口数字变化，而是服务于更长工程链路和更大项目上下文的能力叙事
- `GLM-5.2` 已经公开暴露 `IndexShare`、`MTP` 改进、speculative decoding、sparse-kernel 等架构与推理效率线索，但这些线索仍不等于完整架构复原

## 五、需要保留的证据边界

这个系列最容易被误读的地方，是把不同材料层级混成同一种“官方事实”。更稳的读法是先分清对象：

- **报告对象**：`GLM-5` technical report 本身可单独研究，见 [`glm-5-report.md`](./glm-5-report.md)
- **版本对象**：`GLM-5`、`GLM-5.1`、`GLM-5.2` 分别承接不同版本的公开定位、能力边界和发布形态
- **系列主线**：`agentic engineering`、长程任务、coding / tool-use、长上下文效率优化是系列层面的连续背景
- **变体对象**：highspeed、FP8、平台服务入口或量化入口不应自动提升为和主版本同层的演进节点

因此，阅读或继续扩写本目录时，最重要的边界是：可以用 `GLM-5` 报告解释系列技术背景，但不能把它当成后续每个版本的独立 technical report；可以记录官方能力叙事，但不能把“8 小时持续工作”“项目级工程接管”等表述写成脱离任务条件的固定能力上限。

## 六、如何继续阅读

如果只想建立整体理解，读完本篇即可先抓住 `GLM-5.x` 的主线。继续下钻时，可以按问题选择：目录说明与文件分工见 [`README.md`](./README.md)；跨版本差异见 [`glm-5.x-evolution.md`](./glm-5.x-evolution.md)；具体版本事实见 `glm-5.md`、`glm-5.1.md`、`glm-5.2.md`；原报告本身的技术结构见 [`glm-5-report.md`](./glm-5-report.md)。
