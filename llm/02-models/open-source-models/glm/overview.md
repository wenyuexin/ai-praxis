# GLM 系列总览

## 这个目录承接什么

本目录用于承接 `GLM` 系列开源 / 公开模型的对象研究，尤其是 `GLM-5.x` 这类具有明显版本演进特征的对象。

这里的重点不是把 `GLM` 当成一个静态单体模型，而是保留：

- 系列级定位
- 版本关系
- 不同版本的公开发布形态
- 哪些文档是系列总览，哪些文档是具体版本对象正文

## 这个目录为什么不只保留一篇总文

`GLM-5`、`GLM-5.1`、`GLM-5.2` 并不是可以互相替代的静态对象。

对这类持续演进对象，版本差异可能改变：

- 能力边界
- 上下文长度
- 接口能力
- 技术背景与公开报告关系
- 开源权重发布方式
- 服务形态与变体

因此，本目录不把多版本观察压成单一对象总览；更稳的结构是：

- `overview.md`：承接系列总览与版本关系
- 系列差异整理文：承接跨版本的演进主线与比较阅读入口
- 带版本标识的对象正文：承接具体版本对象研究

## 当前文档分工

- `overview.md`：当前文件，承接 `GLM` / `GLM-5.x` 系列的总览与阅读入口
- `glm-5.x-evolution.md`：承接 `GLM-5` 到 `GLM-5.2` 的版本演进与差异主线
- `glm-5.md`：`GLM-5` 基础版本对象文，也是当前系列技术报告最直接承接的版本节点
- `glm-5.1.md`：`GLM-5.1` 版本对象正文
- `glm-5.2.md`：`GLM-5.2` 版本对象正文
- `notes/`：承接系列内已稳定出现、但暂不足以直接写成版本正文定论的问题层
- 后续如继续研究其他版本，应继续使用带版本标识的对象文件名，而不是把它们混写进目录级总览

## 版本对象文如何命名

本目录遵循以下分工：

- 目录级总览统一使用 `overview.md`
- 具体版本对象正文优先使用带版本标识的对象文件名，如 `glm-5.md`、`glm-5.1.md`、`glm-5.2.md`
- 只有当文档主对象是明确存在的上游 report / technical report / system card / whitepaper 时，才使用 `*-report.md`

这意味着：

- 不因为版本对象文承担快速理解功能，就命名成 `*-overview.md`
- 不因为对象研究引用了某份 report，就默认命名成 `*-report.md`

## 当前可见的系列判断

基于现有公开材料，当前至少可以确认：

- `GLM-5` 报告可作为系列级技术背景
- `GLM-5.1`、`GLM-5.2` 都应优先按版本对象处理
- 系列公开资料常常由 blog、产品文档、模型页、系列仓库与前代技术报告共同构成，不等于“每个版本都有独立技术报告”

## `notes/` 现在承接什么

当前目录已经启用 `notes/`，但它不是新的正文层，也不是 `temp/` 的镜像备份。

这里的 `notes/` 主要承接：

- 系列内反复出现的问题边界
- 已确定属于 `GLM` / `GLM-5.x`，但暂不足以直接写成对象正文定论的材料
- 对后续版本对象文和系列差异文都有影响的稳定问题层

当前已经先落了五类问题：

- `notes/report-boundary.md`
- `notes/parameter-wording.md`
- `notes/release-stages.md`
- `notes/architecture-clues.md`
- `notes/variant-boundary.md`

它们的共同特点是：问题已经稳定存在，但答案还不够适合完全压平成正文事实。

## 后续可扩方向

后续如材料继续增长，本目录可继续长出：

- `glm-5-report.md`（仅当后续明确需要把 `GLM-5` 技术报告本身当作独立研究对象处理，且其职责不再由 `glm-5.md` 承担时）
- 后续其他带版本标识的对象文
- `notes/` 下更多按问题组织的辅助材料（如架构线索、服务变体边界、跨版本规格差异）
