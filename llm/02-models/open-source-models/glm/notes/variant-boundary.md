# GLM-5.x 版本与变体边界笔记

## 这份笔记承接什么

这份笔记专门处理 `GLM-5.x` 系列里“主版本递进”和“服务/部署变体”之间的边界问题。

它要解决的是：

- `GLM-5`、`GLM-5.1`、`GLM-5.2` 是否属于明确的代际递进关系
- `GLM-5.1-highspeed` 这类东西应视为独立模型、独立发布变体，还是服务侧优化入口
- 后续如果出现更多 `FP8`、`highspeed`、托管部署版本，应如何和主版本对象区分

## 当前已知

### 1. `GLM-5 -> GLM-5.1 -> GLM-5.2` 是明确的主版本递进链

当前公开材料已经能较稳支持：

- `GLM-5.1` 相对于 `GLM-5` 是后续旗舰版本
- `GLM-5.2` 相对于 `GLM-5.1` 是后续旗舰版本
- 官方 README 已明确把 `GLM-5.1` 写成 `GLM-5.2` 的 `predecessor`

这意味着当前不宜把三者理解成并列型号池，而更适合理解成同一系列中的连续版本节点。

### 2. `GLM-5.1-highspeed` 更像服务型变体，而不是独立权重模型

当前已整理材料表明：

- 官方有独立文档页承接 `GLM-5.1-highspeed`
- 官方口径强调它是在“完整保留 `GLM-5.1` 能力”的基础上提供高速 API
- 优化重点放在推理引擎、调度系统与基础设施侧
- 当前未见独立的 Hugging Face / ModelScope 权重仓库与独立开源权重发布

因此当前更稳的归类是：

- 它不是新的主版本对象
- 也不像独立权重变体
- 更像平台侧推理优化后的服务型变体 / API 入口

### 3. `FP8` 版本更像部署/量化变体

当前已经能看到：

- `GLM-5.1-FP8`
- `GLM-5.2-FP8`

这类对象有独立权重仓库，但它们的主要价值仍更接近：

- 量化部署形态
- 权重格式 / 推理成本 / 运行条件差异

而不是新的主版本节点。

## 当前更稳的区分原则

### 1. 主版本对象

更适合归为主版本对象的信号包括：

- 官方明确按前后代关系描述
- 有独立的版本对象文档与能力叙事
- 对上下文长度、能力边界、架构线索或发布形态产生明显变化

按当前材料，`GLM-5`、`GLM-5.1`、`GLM-5.2` 属于这一层。

### 2. 服务型变体

更适合归为服务型变体的信号包括：

- 有独立 API 名称或文档页
- 官方重点强调推理引擎、调度、基础设施或平台侧优化
- 强调“保留原模型能力”而不是引入新的独立模型身份
- 没有独立开源权重仓库

按当前材料，`GLM-5.1-highspeed` 更接近这一层。

### 3. 量化/部署变体

更适合归为量化或部署变体的信号包括：

- 名称中直接暴露量化格式或部署形态，如 `FP8`
- 存在独立权重仓库
- 主要差异在推理成本、格式、部署适配，而不是主版本能力身份

按当前材料，`GLM-5.1-FP8`、`GLM-5.2-FP8` 更接近这一层。

## 当前最容易误写的地方

### 1. 把服务型变体误写成主版本升级

`GLM-5.1-highspeed` 即使有独立 API 名与文档页，也不应直接写成与 `GLM-5.2` 同层的主版本节点。

### 2. 把量化仓库误写成系列新版本

`FP8` 版本的存在，更像部署与权重形态差异，而不是“GLM-5.1` 之后又出了一个新的主版本”。

### 3. 把“没有独立权重”误写成“没有独立身份”

也要注意另一侧边界：

- 某些服务型变体可能确实有稳定产品身份
- 只是这种身份不等于版本对象身份

因此后续写法更适合区分：

- 研究对象身份
- 发布对象身份
- 部署/服务入口身份

## 待确认

1. `GLM-5.1-highspeed` 是否与 `GLM-5.1` 使用完全相同的权重文件
2. `GLM-5.2` 后续是否会出现同类 `highspeed` 或其他服务型变体
3. 官方是否会给出更明确的“主版本 vs 变体”命名规则或 release 结构
4. `GLM-5-Turbo` 在官方体系中的定位是否与上述几类之一稳定对应

## 后续动作

1. 如果后续出现新的 `highspeed` / `turbo` / 量化版本，先回到这份笔记判断其属于哪一层
2. 如果某个变体开始出现独立能力边界与版本叙事，再判断是否升格为单独研究对象
3. 在当前阶段，正文提到 `GLM-5.1-highspeed` 时，优先写成服务型变体，而不是系列主版本
