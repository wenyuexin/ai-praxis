# GLM-5.1 发布阶段笔记

## 这份笔记承接什么

这份笔记只处理一个问题：`GLM-5.1` 的多个日期到底是冲突，还是同一版本对象的不同发布阶段。

它的作用是帮助正文避免把多个时间点硬压成一个“发布日期”。

## 当前已知

当前材料中已经出现过至少三个时间点：

- `2026-03-27`：部分用户先开放
- `2026-04-07`：新品发布 / 平台公告
- `2026-04-08`：正式开源

这些时间点来自不同官方链路与已整理材料，但目前看更像一个连续发布过程，而不是互相否定的冲突日期。

## 当前更稳的理解

### 1. 这更像阶段化发布，而不是单点发布

目前更合理的阶段划分是：

1. 先向部分用户开放
2. 再通过官方平台或文档完成正式公告
3. 再完成开放权重发布

如果按这个理解，那么不同材料中的日期差异并不需要强行消掉，而应在对象文中显式区分发布节点类型。

### 2. “发布日期”这个字段本身太粗

如果正文只写一个“发布日期”，很容易混淆：

- 首次可用时间
- 官方公告时间
- 开源时间
- 权重正式上线时间

因此 `GLM-5.1` 这类对象更适合写成“发布节点”而不是单一发布日期。

## 当前正文中的更稳写法

在对象文或后续版本对比中，更稳的写法通常是：

- `2026-03-27`：先向部分用户开放
- `2026-04-07`：新品发布 / 平台公告
- `2026-04-08`：正式开源

如果某处必须简写一句，也更适合写：

- `GLM-5.1` 于 2026 年 4 月上旬完成公开发布，并经历了先开放、再公告、再开源的多个节点

而不是只保留一个日期并删掉其余阶段。

## 为什么这件事值得单独记

这个问题会反复影响至少三类文档：

- `glm-5.1.md` 的发布形态描述
- `glm-5.x-evolution.md` 的版本演进时间线
- 未来如果写 `GLM-5.1-highspeed` 或 `GLM-5.2` 变体关系时，对“版本发布”与“服务更新”的区分

如果不单独记住，后面很容易每次都重新把它误判成“日期冲突”。

## 待确认

1. 系列仓库 release / tag 页面是否存在能更直接对应这三个节点的记录
2. `2026-04-07` 与 `2026-04-08` 在不同官方入口中的角色是否还有更细分的“公告”与“开源上架”区别
3. `GLM-5.1-highspeed` 这类后续变体是否也应沿用“发布阶段”而不是单一发布日期的写法

## 后续动作

1. 如果后续获取官方 release note 或 repo tag，优先补强“每个日期对应什么动作”
2. 如果未来写系列时间线，可直接复用这份阶段划分，而不是重新压成单点日期
3. 如果后续发现某个日期来自第三方误转述，再回到这里修订阶段定义
