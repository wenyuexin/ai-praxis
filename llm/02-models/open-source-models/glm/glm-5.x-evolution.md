## 一、这篇文档承接什么

这篇文档只承接一件事：把 `GLM-5` 到 `GLM-5.2` 之间当前已经较稳的版本演进主线单独抽出来，方便比较“哪一版改变了什么、哪些是连续继承、哪些是增量增强”。

因此，它不是新的证据池，也不是某一版对象正文，而是系列内部的差异整理文。更高层的系列总览负责解释 `GLM-5.x` 的整体背景；本文只聚焦版本之间的变化关系。

## 二、版本关系速览

| 版本 | 核心定位 | 上下文 / 输出口径 |
|------|----------|------------------|
| `GLM-5` | 系列技术锚点；从 `vibe coding` 转向 `agentic engineering` 的基础版本 | 报告中重点讨论长上下文训练与 `200K` context extension |
| `GLM-5.1` | 后续旗舰版本；把 long-horizon task / agent workflow 写成更清晰的版本身份 | 官方稳定给出 `200K` 上下文、`128K` 最大输出 |
| `GLM-5.2` | 后续主版本节点；推进到 `1M` 上下文、项目级工程执行和更明确架构增量 | 官方稳定给出 `1M` 上下文、`128K` 最大输出 |

补充边界：`GLM-5` 直接承接 technical report；`GLM-5.1`、`GLM-5.2` 目前更像回引 `GLM-5` 报告作为系列背景，未发现各自独立的 technical report。发布证据上，后续版本主要由官方博客、产品文档、模型页、ModelScope / Hugging Face、release note 等材料共同承接；因此报告细节不能自动外推到后续版本，`GLM-5.2` 的 `IndexShare` / `MTP` 等线索也不等于完整架构复原。

## 三、当前最清晰的演进主线

如果只看当前已经整理过的公开材料，`GLM-5.x` 的演进方向可以先概括成三步：

1. `GLM-5`：建立从 `vibe coding` 转向 `agentic engineering` 的系列技术锚点
2. `GLM-5.1`：作为 `GLM-5` 之后的后续旗舰版本，沿主架构继续推进，让“长程任务执行”成为更清晰的版本定位，并补齐长上下文、工具调用、结构化输出等 agent 工作流能力
3. `GLM-5.2`：作为 `GLM-5.1` 之后的后续主版本节点，把长程任务叙事进一步推进到 `1M` 上下文、项目级工程执行与更明确的架构级增量

换句话说，这个系列目前不是在做简单的“聊天模型迭代”，而是在持续强化：

- 长链路任务执行
- coding / agentic engineering
- 工具调用与结构化输出
- 长上下文下的工程约束保持
- 更完整的开放发布与部署承接

## 四、分版本看，主变化在哪里

### 4.1 GLM-5：系列技术锚点

`GLM-5` 当前最特殊的地方，不只是“更早”，而是它直接承接了公开技术报告。

因此它在系列中的角色更像：

- 技术路线的基础版本
- `agentic engineering` 叙事的最直接报告锚点
- 后续版本做能力增强时的对照起点

在现有结构里，`GLM-5` 更负责回答：

- 这一代系列最初想解决什么问题
- 为什么路线会从单次代码生成转向更长程的工程执行
- MoE、sparse attention、长上下文效率优化等背景最初如何进入这条路线

### 4.2 GLM-5.1：把“长程任务版本对象”单独立起来

相对 `GLM-5`，`GLM-5.1` 的变化不是只有“参数更新”或“代码更强”。

当前更稳的变化主线包括：

- 明确把 `long-horizon task` / `agentic engineering` 写成版本对象的核心身份
- 把“连续执行、自主迭代、长链路保持”推到更前台
- 官方稳定给出一组 agent workflow 相关能力：`200K` 上下文、`128K` 最大输出、MCP、Function Call、Structured Output、Context Caching
- 公开发布形态开始更清楚地体现为“系列仓库 + 权重页 + 产品文档 + 官方博客”的组合对象
- 在架构边界上，当前更像沿 `GLM-5` 的 `glm_moe_dsa` 主架构继续推进，而不是完全独立的架构改代

因此，`GLM-5.1` 像是在 `GLM-5` 的技术路线之上，把“长程任务模型”从系列口号推进成一个更可识别的版本对象，同时保留了相对前代更连续的主架构继承关系。

### 4.3 GLM-5.2：把长程任务能力推向更强发布形态

相对 `GLM-5.1`，`GLM-5.2` 当前最清晰的升级集中在四件事：

- 上下文窗口从 `200K` 推进到 `1M`
- 官方叙事更强地转向项目级工程执行、长程重构、多步骤持续约束保持
- 开放权重、`MIT` 许可、Hugging Face / ModelScope / 系列仓库 / 产品文档的发布承接方式更完整可见
- 官方已开始更直接暴露架构级增量，而不只是能力卖点

与此同时，`GLM-5.2` 公开材料里已出现更明确的技术增量表述，例如：

- `IndexShare`
- 对 `MTP` 层的改进，用于 speculative decoding
- 在超长上下文下控制 FLOPs 与提高 acceptance length 的方向
- 相对 `GLM-5.1` 的 `IndexShare DSA` / `TileLang sparse-kernel` 方向增量

这些线索说明 `GLM-5.2` 不只是能力宣传更强，也开始在公开材料里暴露更多“为什么这一版能把长程任务推得更远”的技术端口；因此它相对 `GLM-5.1` 的变化，已经不只是一组更强的产品口径，而是带有更清楚架构增量边界的后续主版本升级。

## 五、横向对比：哪些能力是连续继承，哪些是明显升级

### 5.1 连续继承的主线

从 `GLM-5` 到 `GLM-5.2`，至少有几条线是持续不变或持续强化的：

- 系列一直围绕 `agentic engineering` 理解自己
- coding 能力强调的不只是一次生成，而是多步骤执行
- tool-use / workflow integration 一直是重要方向
- 长上下文不是孤立卖点，而是为长链路任务服务
- 大规模 MoE 与稀疏注意力相关路线始终是重要背景

### 5.2 明显升级的主线

当前最清楚的代际增强主要发生在：

- 长上下文规模：`GLM-5.1` 为 `200K`，`GLM-5.2` 为 `1M`
- 主版本递进关系：从 `GLM-5` 到 `GLM-5.1` 再到 `GLM-5.2`，官方已更明确地给出前后代节点关系，而不是仅靠读者自行推断
- 长程任务叙事强度：从系列技术路线，推进到版本对象级核心卖点
- 工程任务粒度：从一般 coding / tool-use，推进到项目级工程接管、迁移、重构与规范保持
- 公开发布形态：从系列技术报告锚点，逐步发展为更完整的开放权重发布与部署入口组合
- 架构变化可见度：`GLM-5.1` 更像沿 `GLM-5` 主架构继续推进，而 `GLM-5.2` 已开始公开暴露更明确的架构级增量

## 六、当前最值得保留的版本边界

### 6.1 不要把 GLM-5 报告当成每一版的独立报告

当前一个最重要的边界是：

- `GLM-5` 有直接技术报告承接
- `GLM-5.1`、`GLM-5.2` 当前没有发现各自独立的 technical report
- 后续版本经常回引 `GLM-5` 报告作为系列背景

所以更稳的理解是：

- `GLM-5` 负责承接系列基础技术路线
- `GLM-5.1`、`GLM-5.2` 负责承接版本增量变化与公开发布信息

### 6.2 不要把版本规格写成跨版本静态事实

当前仍需要保守处理的边界包括：

- `GLM-5` 的训练细节、参数规模、benchmark 不能自动外推到 `GLM-5.1` 或 `GLM-5.2`
- `GLM-5.1` 与 `GLM-5.2` 各自公开页里的参数口径仍有待更直接材料统一
- `GLM-5.1` 的 `updated weights` 不等于我们已经拿到了它的完整 config 差异说明
- `GLM-5.2` 的 `IndexShare` / `MTP` 增量已可较稳确认存在，但仍不等于可以直接写成完整架构复原
- “8 小时持续工作”“项目级工程接管”等表述，更适合写成官方能力叙事，而不是脱离任务条件的固定上限

### 6.3 不要把服务型变体和量化变体误并入主版本链

当前更稳的边界是：

- `GLM-5`、`GLM-5.1`、`GLM-5.2` 承接主版本递进链
- `GLM-5.1-highspeed` 更像服务型变体 / 平台侧推理优化入口
- `GLM-5.1-FP8`、`GLM-5.2-FP8` 更像量化或部署变体

因此，系列演进主线应优先围绕主版本节点展开，不要把服务入口或量化仓库直接提升为同层版本节点。

### 6.4 不要把系列演进文误写成总览或单版正文

这篇文档的边界也要明确：

- 它不是完整系列总览，不负责展开 `GLM-5.x` 的全部背景理解
- 它不是 `glm-5.md`、`glm-5.1.md`、`glm-5.2.md` 的替代品
- 它只负责抽取差异主线，不负责重新展开每一版的全部证据

## 七、如何使用本文

如果只想快速比较版本关系，优先读第二、三、四节；如果关心能力继承与升级，再读第五节；如果关心边界风险，再读第六节；如果需要追到某一版的具体证据，再回到对应版本对象文。

外部分发时，可以把本文当作 `GLM-5.x` 的版本关系说明，而不是完整技术报告。它可以帮助避免两种常见误读：

- 误把某一版对象文当成整个系列说明书
- 误把系列技术路线背景写成每个版本都已独立验证的事实

## 八、后续最值得继续补强的比较问题

如果后续继续扩写，这篇文档最值得补强的方向包括：

1. `GLM-5.1` 到 `GLM-5.2` 的能力变化，哪些已有更直接官方对照材料
2. `200K` 到 `1M` 的上下文提升，是否伴随更明确的任务类型边界变化
3. `GLM-5.2` 暴露的架构优化线索，是否能在源码、模型卡或后续报告中找到更直接解释
4. 开放权重发布与本地部署支持，在 `GLM-5.1` 和 `GLM-5.2` 之间是否存在更具体的承接差异
